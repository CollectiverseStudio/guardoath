# Input-validation expansion — implementation progress

Updated 2026-10-29. This document records **implemented foundations** for the [expansion roadmap](input-validation-expansion-roadmap.md), not claims that full semantic protection or production ingress enforcement exists.

## IV-03: Offline effectiveness metrics — initial implementation

`guardoath/effectiveness.py` exposes `Observation(case_id, attack, flagged, latency_ms)` and `summarize(...)`. The result includes TP, FP, TN, FN, recall, false-positive rate, bypass rate, and interpolated P50/P95/P99 latency. When a denominator is zero, the corresponding rate is `null`/Python `None`, rather than a misleading 0%. Duplicate case IDs, negative latency, NaN and infinity are rejected.

`tests/test_effectiveness.py` covers confusion counts, denominators, empty and single-class data, duplicate IDs and invalid latency. This is **offline accounting only**: it does not execute GuardOath checks, collect live traffic, calculate confidence intervals, or measure actual detection effectiveness. Source data must be independently labeled and generated by an authorized evaluator. Do not interpret passing tests as measured detection recall.

## IV-02: Untrusted-content provenance envelope — initial implementation

`guardoath/untrusted_content.py` defines explicit `user_input`, `retrieved_document`, and `tool_response` surfaces, plus tenant, application and source IDs and bounded UTF-8 text. `assessment_metadata()` omits the content itself and returns only provenance identifiers. `tests/test_untrusted_content.py` covers all surfaces, forged source IDs inside payloads, missing provenance and size limits.

This **does not detect or sanitize prompt injection** and is not connected to FastAPI, retrieval, agent context, tool dispatch or AI ingress. The host must supply authenticated provenance and keep lower-trust content out of system/developer instruction roles. The metadata envelope is not a security boundary by itself.

## IV-03 extension: strict paired evaluation comparison

`guardoath/evaluation_comparison.py` adds `EvaluationRun` and `compare_runs` for comparing two *already scored* runs. Each run records dataset ID/version, policy version, checker version and source commit. The comparison **rejects different dataset versions, missing/extra case IDs and changed ground-truth labels** instead of silently calculating misleading deltas. Case ordering may differ.

It reports recall, false-positive and bypass-rate deltas (or `None` for undefined denominators), and explicit case IDs for newly missed attacks and newly flagged benign samples. `tests/test_evaluation_comparison.py` covers positive regressions, shuffled order, mismatched datasets, missing IDs, altered labels, empty/single-class runs, invalid provenance and duplicate IDs.

**Not implemented:** dataset acquisition, ground-truth labeling, automated execution of GuardOath policies, cryptographic provenance, artifact signing, confidence intervals, statistical significance, paid-provider usage, live drift detection, or production CI gating. The new comparison module cannot establish that a real model is secure. Use independent held-out datasets before interpreting rates. These are new files; no existing tests or reserved source files were modified. GitHub CI verification remains separate.


## IV-03 extension: saved local evaluation report adapter

`guardoath/evaluation_adapter.py` converts a `guardoath.evaluate.evaluate(...)` report into `Observation` objects for the existing metrics and paired comparison modules. The caller **must** provide a complete independent mapping of `case_id → attack/benign` boolean labels; the regression `matched` flag is never used as a security ground-truth label. A detection is defined narrowly as a nonempty finding ID list or a checker status of `flagged`.

The adapter rejects duplicate case IDs, missing/extra/nonboolean labels, unsupported execution scopes, regression mismatches, incomplete or simulated results, and missing/error/skipped/unsupported checker outcomes. It does not echo prompt content. `tests/test_evaluation_adapter.py` exercises positive/benign metrics, false positives, invalid labels, incomplete outcomes, malformed reports and duplicate IDs.

**Important limitations:** This is an opt-in Python API, not yet invoked automatically by `guardoath.evaluate` or CI. The reviewed labels are supplied by a trusted evaluator, not inferred from existing expected findings. A report containing heterogeneous checks or unreviewed threat labels may not yield meaningful attack recall. No confidence intervals, production sampling, privacy-sensitive data retention, cost measurement or enforcement claims are provided. Run the new tests in CI before treating this integration as verified.


## IV-03 extension: end-to-end local labeled evaluation workflow

`guardoath/labeled_evaluation.py` now composes the existing local suite loader, policy loader, Engine, regression evaluator, independently supplied label adapter, metrics and paired comparison. `run_labeled_suite` requires explicit `case_id → bool` labels for every evaluated case and provenance fields (dataset version, checker version, source commit). It rejects incomplete/simulated/mismatched cases through the adapter; it does not infer ground truth from expected findings. `compare_labeled_suites` applies strict paired-run comparison.

`tests/test_labeled_evaluation.py` exercises the actual saved `evals/text-security.json` and `policies/text-security.json` locally, including missing-label rejection, metric totals and a same-suite comparison. **Fixture classifications are synthetic demonstrations, not independently adjudicated adversarial labels.** Thus the resulting numbers are not real-world security detection rates. The workflow runs local checks only and does not transmit data to external providers.

**Limitations:** opt-in Python API only, no CLI flags or CI effectiveness gate, no output artifact persistence/signing, no confidence intervals, no live semantic provider benchmarking, and no downstream ingress enforcement. The tests must pass in GitHub Actions before the new workflow is considered verified. Do not modify reserved `guardoath/evaluate.py`, `guardoath/app.py`, `guardoath/engine.py` or shared policies without coordination.
