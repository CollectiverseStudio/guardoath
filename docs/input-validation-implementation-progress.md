# Input-validation expansion — implementation progress

Updated 2026-10-29. This document records **implemented foundations** for the [expansion roadmap](input-validation-expansion-roadmap.md), not claims that full semantic protection or production ingress enforcement exists.

## IV-03: Offline effectiveness metrics — initial implementation

`guardoath/effectiveness.py` exposes `Observation(case_id, attack, flagged, latency_ms)` and `summarize(...)`. The result includes TP, FP, TN, FN, recall, false-positive rate, bypass rate, and interpolated P50/P95/P99 latency. When a denominator is zero, the corresponding rate is `null`/Python `None`, rather than a misleading 0%. Duplicate case IDs, negative latency, NaN and infinity are rejected.

`tests/test_effectiveness.py` covers confusion counts, denominators, empty and single-class data, duplicate IDs and invalid latency. This is **offline accounting only**: it does not execute GuardOath checks, collect live traffic, calculate confidence intervals, or measure actual detection effectiveness. Source data must be independently labeled and generated by an authorized evaluator. Do not interpret passing tests as measured detection recall.

## IV-02: Untrusted-content provenance envelope — initial implementation

`guardoath/untrusted_content.py` defines explicit `user_input`, `retrieved_document`, and `tool_response` surfaces, plus tenant, application and source IDs and bounded UTF-8 text. `assessment_metadata()` omits the content itself and returns only provenance identifiers. `tests/test_untrusted_content.py` covers all surfaces, forged source IDs inside payloads, missing provenance and size limits.

This **does not detect or sanitize prompt injection** and is not connected to FastAPI, retrieval, agent context, tool dispatch or AI ingress. The host must supply authenticated provenance and keep lower-trust content out of system/developer instruction roles. The metadata envelope is not a security boundary by itself.
