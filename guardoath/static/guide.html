How it fits in

  1. Your user sends a message. Your application sends it to POST /v1/checks/input.
  2. Only if the input check lets it through, send the message to your AI model.
  3. Send the model's answer to POST /v1/checks/output.
  4. Only if the output check lets it through, show the answer to your user.

GuardOath does not call an AI model and does not write answers. It checks what you send and tells you what to do with it. You can try the four steps without writing code in the check playground.

Get an API key

Keys look like gok_<tenant id>_<secret>. Each key belongs to one tenant record, which holds your checks, your settings and your monthly usage. Your tenant id is the part between gok_ and the next _; you send it as application_id.

  • To try it: pick a demo user in the check playground and select Get demo API key, or call POST /v1/demo-users/demo1/key with the body {}. Demo users are shared: anyone who picks the same one uses the same settings and the same 2,000 checks a month. Do not send real personal data through a demo user.
  • For your application: sign in using Google through the configured Cognito provider on the dashboard. Registering creates an account but does not activate a paid subscription. An independently verified active subscription is required before you can run customer checks. When entitled, use Create API key; a key is shown once and only a fingerprint of it is stored. You can keep at most 2 keys and revoke them. Keep keys on your server, never in a web page or mobile app. Checkout and billing-portal routes exist, but production checkout requires configured server-owned Stripe credentials and price; subscription reconciliation and verified live payment onboarding have not been release-accepted. A redirect alone never activates validation.
  • A key only runs checks. Changing a customer record's checks and keys needs a signed-in session, so a leaked key cannot change your settings. Demo users have no accounts: their demo key can change their own demo record.

Send a check

Base address: https://guardoath.com. Every request with a body is JSON over HTTPS and needs these headers:

HeaderValue
X-GuardOath-KeyYour API key.
Content-Typeapplication/json (UTF-8).
x-amz-content-sha256The SHA-256 of the exact body bytes you send, as 64 lower-case hex characters. Without it the request is refused with HTTP 403. Hash the same bytes you send: serialize the JSON once and use that string for both the hash and the body.

Use X-GuardOath-Key, not Authorization: on guardoath.com the Authorization header is replaced before it reaches GuardOath.

Check request fields

FieldRequiredWhat it is
application_idyesYour tenant id (1–100 characters).
contentyesThe message or answer to check, 1–32,000 characters. For JSON content, send the JSON as a string.
content_formatnotext (default) or json. JSON checks (schema, field comparisons, decision records, citations, tool calls, ledger, timestamps, graph) need json.
policy_versionnoLeave it out, or send tenant: a tenant key always runs the checks on your record. Any other value is refused (404) and not counted.
request_contextnoUp to 8,000 characters of context. Accepted, but not inspected by the current checks.
languagenoen, the only supported value.

Any other field is refused with HTTP 422.

Python (standard library only)

import hashlib
import json
import urllib.error
import urllib.request

API = "https://guardoath.com"
KEY = "gok_demo1_..."          # your API key; keep it on your server
APPLICATION_ID = "demo1"       # your tenant id: the part of the key after "gok_"

def check(stage, content):
    """stage is "input" (the user's message) or "output" (the AI's answer).
    The checks that run are the ones on your record."""
    request = {"application_id": APPLICATION_ID, "content": content}
    body = json.dumps(request).encode("utf-8")
    call = urllib.request.Request(API + "/v1/checks/" + stage, data=body, method="POST", headers={
        "X-GuardOath-Key": KEY,
        "Content-Type": "application/json",
        "x-amz-content-sha256": hashlib.sha256(body).hexdigest(),  # SHA-256 of these exact bytes
    })
    try:
        with urllib.request.urlopen(call, timeout=20) as response:
            return json.load(response)
    except urllib.error.HTTPError as error:
        raise RuntimeError(f"GuardOath answered HTTP {error.code}: {error.read().decode()}") from None

result = check("input", "Please email jane@example.com about my order.")
print(result["effective_action"], [f["rule_id"] for f in result["findings"]])

JavaScript (Node.js)

import { createHash } from "node:crypto";   // Node.js 18 or later

const API = "https://guardoath.com";
const KEY = process.env.GUARDOATH_KEY;      // keep the key on your server
const APPLICATION_ID = "demo1";

async function check(stage, content) {   // the checks that run are the ones on your record
  const body = JSON.stringify({ application_id: APPLICATION_ID, content });
  const response = await fetch(`${API}/v1/checks/${stage}`, {
    method: "POST",
    headers: {
      "X-GuardOath-Key": KEY,
      "Content-Type": "application/json",
      "x-amz-content-sha256": createHash("sha256").update(body, "utf8").digest("hex"),
    },
    body,
  });
  if (!response.ok) throw new Error(`GuardOath answered HTTP ${response.status}: ${await response.text()}`);
  return response.json();
}

Read the result

A check returns HTTP 200 with a result like this (shortened):

{
  "check_id": "6f1c...",                 "application_id": "demo1",
  "policy_version": "tenant",            "stage": "input",          "mode": "enforce",
  "evaluation_status": "complete",       "recommended_action": "block",   "effective_action": "block",
  "findings": [{"rule_id": "pii.email_address", "category": "pii", "severity": "high",
                "explanation": "..."}],
  "checker_results": [{"checker_id": "pii", "status": "flagged", "latency_ms": 3.1, ...}, ...],
  "redaction": {"status": "not_requested", "content": null, "explanation": "..."},
  "groups": [...],  "total_latency_ms": 12.4,  "simulated": false
}
FieldMeaning
effective_actionWhat to do now: allow, flag, redact or block. In observe mode generally allows completed findings for review, but incomplete enabled PII, encoded-PII or Secrets scans and failed mandatory redaction rechecks force block even in observe mode.
recommended_actionWhat the checks found, whatever the mode. In observe mode, this shows what enforce mode would do.
evaluation_statuscomplete, or incomplete when a required check did not finish (for example it timed out). Incomplete is never a pass: the record's normal failure_action is applied except that incomplete enabled PII, encoded-PII, Secrets or withheld mandatory redaction rechecks force an effective Block regardless of observe mode or Flag.
findingsWhat was found: rule_id, category, severity and a plain-language explanation. Findings never repeat the text that matched.
checker_resultsOne entry per check that ran, with status (passed, flagged, error, skipped, unsupported) and, on errors, an error_code.
redactionFor the redact action: status ready (enforce) or preview (observe) with the cleaned content, which has been checked again; withheld when no safe cleaned version exists (recommended_action is then block); not_needed or not_requested otherwise.
mode, policy_version, stageThe mode and profile that ran, and whether this was the input or output check.

Deciding what to do

def next_step(result):
    # effective_action is the decision. A check that did not finish gets your record's failure_action (block or flag).
    action = result["effective_action"]
    if action == "block":
        return "stop"                      # only Block stops a message or answer
    if action == "redact":
        if result["redaction"]["status"] == "ready":
            return "continue with result['redaction']['content']"
        return "stop"                      # no safe cleaned version
    return "continue"                      # allow, or flag: send it on; log flagged findings for review

Only block stops a message or answer. flag means "found something worth a look": the message still goes to the AI model (or the answer to your user), and the findings are reported so you can review them. allow also goes through, with any findings reported.

Each action names a supported tool (shell.run, http.request, file.write, file.delete), an exact target, and bounded arguments. The API compares canonical descriptions and returns matching_unverified, mismatch, or no_observation; every result says authorization: not_granted and verified_execution: false. It never executes, authorizes, stores or attests an action. Data is caller reported, not trusted endpoint telemetry. The dashboard has ready-to-run examples; only synthetic data should be used for demos. Incorrect or oversized descriptions are rejected, and no action content is echoed in findings. A matching report is NOT evidence that execution occurred. This endpoint is separate from the tenant-controlled Input/Output validators and the optional Sigma Windows event preview.

The API reference lists every field of every endpoint. Its "Try it out" buttons cannot add the body hash, so use the examples above to send requests.

Checks

Each check has two fields on your record, one per stage: input_check_<id> for the user’s message and output_check_<id> for the AI’s answer. Each is set to the action taken when the check finds something on that stage: block, flag, allow (report and let it through) or, for personal data only, redact. An empty field (null) means the check does not run on that stage, so a check can block on input and only flag on output, or run on one stage only. Some checks need settings, such as a JSON Schema; demo users have them filled in.

Personal data (PII) input_check_pii output_check_pii

What it checks: Finds personal identifiers: email addresses, card numbers (with a checksum), U.S. Social Security numbers, and 90 more types of bank, tax, health, ID-document, network, phone and postal identifiers for the U.S. and 17 other countries. It can also look for labeled phone, birth date, medical record, health plan and bank account fields.

Why use it: Stop customers’ personal data from being sent to an AI model, or from leaking out in an AI answer. Redact replaces what it finds and checks the result again.

Limits: Does not detect names, places or other free-text personal details.

Input and output, each set separately · Actions: Block, Flag, Allow, Redact · Options: detect_labeled_sensitive_data, privacy_patterns, disabled_privacy_entities, privacy_min_score

Encoded personal data input_check_encoded_pii output_check_encoded_pii

What it checks: Looks for the same personal identifiers inside one labeled Base64 or hex layer, such as “base64: …”.

Why use it: Someone can encode an email or card number to slip it past a plain-text filter.

Limits: One labeled layer only; unlabeled or nested encodings are not decoded.

Input and output, each set separately · Actions: Block, Flag, Allow · No settings needed

Secrets and credentials input_check_secrets output_check_secrets

What it checks: Finds credentials from selected providers, JWTs, private keys and passwords inside URLs. Optionally also quoted password assignments, labeled encoded secrets and your own confidential phrases (for example an internal project name).

Why use it: Stop API keys, passwords or confidential names from being pasted into a model or shown in an answer.

Limits: Selected formats only; credentials are never verified with the provider.

Input and output, each set separately · Actions: Block, Flag, Allow · Options: detect_secret_assignments, inspect_encoded_secrets, confidential_terms

Hidden text and encodings input_check_text_security output_check_text_security

What it checks: Finds selected invisible and control characters, characters that reverse text direction, and labeled Base64/hex text.

Why use it: Hidden characters and encodings are used to smuggle instructions past people reviewing a conversation.

Limits: Not a prompt-injection detector: a plainly worded attack passes.

Input and output, each set separately · Actions: Block, Flag, Allow · No settings needed

Prompt attacks (wording) input_check_prompt_attack output_check_prompt_attack

What it checks: Looks for wording patterns of prompt attacks, including some two-, three- and four-message conditioning in submitted JSON chat: no-rules personas such as DAN, developer or opposite modes, role-play and hypothetical framing used to get around rules, instruction overrides (new instructions, end of system prompt, fake assistant replies, forget your instructions, never refuse), requests for the hidden prompt, instructions hidden in documents or pages for an AI that reads them, decode-then-obey, and answers that show an attack worked.

Why use it: Stop or review a message, document or page that tries to take over your AI's instructions, and an answer that shows it worked. GuardOath checks this itself: nothing is sent to an outside service.

Limits: Matches wording, not general intent: only bounded conditioning split across two or three consecutive submitted JSON chat turns is recognized. Longer, reworded or unstated-context attacks can pass; quoted benign discussions can match. Client-supplied roles are not verified history. Flag suits most uses; Block suits agents that act on what they read.

Input and output, each set separately · Actions: Block, Flag, Allow · No settings needed

Risky instructions (wording) input_check_lexical_guards output_check_lexical_guards

What it checks: Looks for 161 wording patterns of risky instructions: requests to reveal a system prompt or secrets, to ignore instructions or get around safety, approval and audit steps, destructive or data-exposing commands for shells, databases, Git, Kubernetes and cloud accounts, and settings that turn security controls off.

Why use it: Report a message that asks an AI agent to do something dangerous, or an AI answer that proposes it, so a person can review it before anything runs.

Limits: Matches wording, not intent: harmless text that uses the same words is reported too, and reworded requests pass. Flag suits it better than Block.

Input and output, each set separately · Actions: Block, Flag, Allow · No settings needed

Human safety input_check_human_safety output_check_human_safety

What it checks: Looks for 61 wording patterns that a person may be at risk, or that an answer could harm someone: self-harm and suicide, medical emergencies, unsafe medicine use, eating disorders, risks to children, household and machine hazards, stalking, extortion and coercion, scams and gambling, false professional claims, and violence.

Why use it: Make sure a person in crisis gets support (in the U.S., 988 for a suicidal crisis; local emergency services for immediate danger), and stop an AI answer that could hurt someone before it is shown.

Limits: Matches wording, not intent or medical facts: reworded messages pass and harmless text with the same words is reported. Not a clinical or crisis assessment. Flag suits input (offer support, never refuse help); Block suits output.

Input and output, each set separately · Actions: Block, Flag, Allow · No settings needed

Harmful content (wording) input_check_harmful_content output_check_harmful_content

What it checks: Looks for 30 wording patterns of harmful content: hate against groups of people (dehumanizing, calls for violence, claims of inferiority, exclusion), insults and harassment, threats (to hurt, to a family, bombs, shootings, doxxing), sexual content involving minors and other explicit requests, violent extremism, and requests for violence such as poisoning, hiring a hitman, trafficking or making hard drugs.

Why use it: Review or stop hateful, threatening, sexual or violent text before your AI acts on it or anyone sees it. GuardOath checks this itself: nothing is sent to an outside service.

Limits: Matches wording, not meaning: reworded content passes, and quoted, reported or educational text with the same words is reported. Hate rules cover the groups they name. Flag suits input; Block suits output.

Input and output, each set separately · Actions: Block, Flag, Allow · No settings needed

JSON structure (schema) input_check_schema output_check_schema

What it checks: Checks that JSON content matches your JSON Schema: required fields, data types, formats such as dates and emails, and size limits.

Why use it: When your application expects structured data, reject a malformed request or AI answer before your code uses it.

Limits: Needs JSON content and a schema on the record. It checks shape, not whether the values are true.

Input and output, each set separately · Actions: Block, Flag, Allow · Needs: input_schema or output_schema (filled in for demo users)

Field comparisons input_check_cross_field output_check_cross_field

What it checks: Compares two fields in the submitted JSON, for example a start date before an end date, or a refund no larger than the purchase.

Why use it: Catch inconsistent values, such as an AI offering a refund bigger than the order.

Limits: Both values come from the submission, so it is a consistency check, not an authoritative limit.

Input and output, each set separately · Actions: Block, Flag, Allow · Needs: comparisons (filled in for demo users)

Required sections input_check_completeness output_check_completeness

What it checks: Checks that required labeled sections are present and long enough. The demo requires “Summary:” in the message, and “Summary:” and “Next steps:” in the answer.

Why use it: Make sure an AI answer includes the parts your process needs, such as next steps in a support reply.

Limits: Checks that a section exists and its length, not whether its content is good.

Input and output, each set separately · Actions: Block, Flag, Allow · Needs: required_sections (filled in for demo users)

Matched outcomes (bias) input_check_matched_outcomes output_check_matched_outcomes

What it checks: Compares submitted decision records. If two records match except for a group attribute (in the demo, “group”) but got different decisions, it reports a finding.

Why use it: Spot inconsistent decisions between groups, for example in loan or hiring recommendations.

Limits: Needs structured records. It does not judge free-text bias or certify fairness.

Input and output, each set separately · Actions: Block, Flag, Allow · Needs: matched_outcomes (filled in for demo users)

Citation evidence input_check_evidence output_check_evidence

What it checks: Checks that an answer’s [[source]] citations and quotations match a source catalog on the record, word for word.

Why use it: Catch made-up citations and misquoted policy text before an answer reaches your user.

Limits: Not a fact checker: it does not judge whether a quote supports the claim.

Input and output, each set separately · Actions: Block, Flag, Allow · Needs: evidence (filled in for demo users)

Proposed tool calls input_check_tool_calls output_check_tool_calls

What it checks: Checks that tool calls proposed by an AI use allowed tool names and that their arguments match each tool’s schema. The demo allows lookup_order and request_refund.

Why use it: Stop an AI agent from calling a tool it should not use, or passing it bad arguments.

Limits: Nothing is run or authorized; your application still decides whether to make the call.

Input and output, each set separately · Actions: Block, Flag, Allow · Needs: tool_calls (filled in for demo users)

Ledger totals input_check_ledger output_check_ledger

What it checks: Checks that debit and credit entries add up exactly, in a set currency and number of decimal places (demo: USD, 2 places).

Why use it: Catch arithmetic mistakes in financial summaries an AI produces.

Limits: Exact arithmetic only; no fraud or accounting-rule checks.

Input and output, each set separately · Actions: Block, Flag, Allow · Needs: ledger (filled in for demo users)

Timestamp order input_check_timestamps output_check_timestamps

What it checks: Checks that a list of timestamps is in order, with no earlier time after a later one.

Why use it: Catch out-of-order event logs and timelines.

Limits: No sorting, freshness checks or memory between requests.

Input and output, each set separately · Actions: Block, Flag, Allow · Needs: timestamps (filled in for demo users)

Graph structure input_check_graph output_check_graph

What it checks: Checks a declared directed graph for cycles, self-loops, duplicate edges and links to unknown nodes.

Why use it: Validate workflow or dependency graphs before they are used.

Limits: Checks the declared structure only, not whether the relationships are true.

Input and output, each set separately · Actions: Block, Flag, Allow · Needs: graph (filled in for demo users)

Content integrity (SHA-256) input_check_integrity output_check_integrity

What it checks: Checks that content’s SHA-256 fingerprint matches an approved reference stored on the record.

Why use it: Confirm that a template, policy text or file has not changed by even one character.

Limits: A match shows the bytes are unchanged, not that the content is safe.

Input and output, each set separately · Actions: Block, Flag, Allow · Needs: integrity (filled in for demo users)

CSV spreadsheet formula protection input_check_csv_formula output_check_csv_formula

What it checks: Checks CSV text as spreadsheet cells and flags leading formula triggers (=, +, -, @), including quoted and whitespace-prefixed cells.

Why use it: Prevent user-controlled CSV exports or AI-generated CSV answers from being opened as executable spreadsheet formulas.

Limits: Use only for CSV text, not ordinary chat. This is a detection signal, not a sanitization or spreadsheet execution guarantee; negative numbers may be flagged.

Example: name,entry followed by a row Alice,=1+2 reports csv_formula.potential_formula; a cell that starts with an apostrophe ('=1+2) is the look-alike. Malformed CSV, JSON content or more than 1,000 rows, 256 columns or 4,000 cells give an incomplete result, which follows the record’s failure action. Saved evaluation cases: evals/csv-export.json.

Input and output, each set separately · Actions: Block, Flag, Allow · Text only · No settings needed

Change your checks

Sign in on the dashboard and change your checks there, or send POST /v1/tenants/current/checks with your session (header X-GuardOath-Session; demo users send their demo key) and your record's current revision (from GET /v1/applications/current) and the fields to change:

{"revision": 3, "changes": {"input_check_pii": "redact", "output_check_pii": "block", "output_check_text_security": null, "output_rule_actions": {"pii.ip_address": "off"}}}
  • You can change: every input_check_<id> and output_check_<id> field, the check settings, input_rule_actions and output_rule_actions (one rule off, or its own action, on that stage; the names check_<id> and rule_actions were used before 2026-11-04 and are refused), mode (enforce or observe), timeout_ms (1–5,000) and failure_action (block or flag).
  • At least one check must stay on. A change that is refused says why (HTTP 422) and changes nothing.
  • If the record changed since you read it, you get HTTP 409: read the revision again and resend.
  • Changes apply from the next check and are not counted as checks. Demo users can go back to the starting values with POST /v1/tenants/current/reset (body {}).

Statistical drift: batch PSI through the dashboard

Sign in as a tenant settings owner (or connect to your own demo tenant) and open Statistical drift (PSI) batch rules inside Checks on this record. Add an ID, a JSON pointer to an array of numeric observations, a tenant-supplied versioned reference ID, strictly ascending numeric bin edges, matching integer reference bin counts, a PSI threshold and a minimum batch size. Choose Input, Output or both, click Add to pending changes, enable Field comparisons for those stages, and click Save checks. The saved rule appears under the normal Field comparisons rules and uses the same per-stage Block, Flag, Allow and Off actions as all other tenant rules. Edits/removals use the same revisioned save; stale saves return 409 without overwriting the tenant.

For a synthetic example, click Fill synthetic PSI sample, add the rule, configure Input Field comparisons to Block, and Save checks. Click Load synthetic shifted batch into Input data, then Run input checks to obtain an actual tenant-engine evaluation, not a fake dashboard result. The deliberately shifted batch should report business.ui_psi_demo with the configured tenant action. A small batch gives an insufficient sample finding, not a clean stability claim. Output can be checked independently after an accepted Input. The sample reference is fabricated for demonstration only.

Private reference histograms are not distributed in the normal application summary. The dashboard reads them through owner-only GET /v1/tenants/current/statistical-drift, which responds with the current tenant revision and rules (production API keys without a signed-in owner session receive 403). The UI is a way to manage a tenant-supplied baseline; it does not verify the external provenance of that baseline, collect continuous telemetry, assess natural-language intent, or prove model output safety. Use source-approved reference data, retention controls, domain calibration and independent validation for real deployments.

Security event rules (SigmaHQ) — tenant-owned

Each tenant now has its own sigma_rule_actions map. The 228 pinned Windows process/PowerShell event rule IDs appear in the tenant's settings panel, with separate Off (default), Allow, Flag or Block actions. These are security-event signatures, not AI input or output message validators. They do not run in the conversation workflow. Saving a rule uses the usual authenticated, revision-checked tenant update /v1/tenants/current/checks.

GET /v1/sigma/catalog is written /v1/sigma/catalog in the API reference; it returns pinned source metadata and use cases for an authenticated tenant without distributing synthetic fixture contents. POST /v1/sigma/demo (/v1/sigma/demo) is the synthetic rule-test endpoint: the request contains only rule_id (an original pinned SigmaHQ UUID) and sample (positive or lookalike).

The server authenticates the tenant, reads that tenant's currently saved sigma_rule_actions, refuses Off or unrecognized rules and uses a server-owned pinned example, trusted Windows logsource and one bounded event-evaluation budget. It responds with a source-attributed match plus recommended_action and effective_action based on the tenant record's mode; it does not execute a Windows command or ingest customer logs. An Input or Output check never invokes Sigma. Live Windows-event ingestion, trusted source attestation and SIEM transport are not implemented by the synthetic preview.

The separate /sigma page is an optional event evidence explorer. Tenant selection and per-rule actions live primarily in the same tenant settings panel as the other checks. A saved Block or Flag rule can be exercised through the panel's bundled synthetic examples. Demo records are shared, so use synthetic data only. There are no paid provider calls from this isolated feature.

CSV and TSV file attachments (authenticated tenant check)

For actual uploaded file bytes sent in strict JSON Base64, use /v1/checks/input/attachments or /v1/checks/output/attachments. Both are authenticated tenant-only variants of the existing check flow; each runs the normal chat check and the supported per-file CSV/TSV spreadsheet formula rule, keeps the same tenant settings and counts a request once. At GuardOath's AWS edge, send X-GuardOath-Key and x-amz-content-sha256 of the exact UTF-8 JSON body.

Additional fieldRequiredWhat it means
attachments_b64yes (attachment endpoints only)1–3 strict Base64 strings representing actual received bytes (not file names, MIME labels or prompt text). Each file has a 32,000 decoded-byte inspection budget; larger or unsupported data is incomplete and blocked rather than reported clean.

New tenants and existing saved tenant records missing input_attachment_csv_mode or output_attachment_csv_mode default that stage to auto; attachment-specific inspection activates only when real file bytes are provided. An explicitly persisted off remains Off and is reported as not inspected, not clean. Older software may have saved a default Off indistinguishable from an intentional opt-out: audit provenance before any targeted change. Use the normal revisioned /v1/tenants/current/checks endpoint to change an authorized tenant setting. In Auto, any existing input_check_csv_formula or output_check_csv_formula action is used; otherwise a formula finding defaults to Block. Individual rule Off still wins. A clean recognized CSV or TSV passes the file rule; an explicit Off is reported not_inspected_policy_off, not passed.

Tab-delimited UTF-8 tables are identified from received bytes when the first record contains a tab and no comma, followed by consistent columns and at least two records. A TSV with an unescaped formula cell such as =2+3 uses the same tenant csv_formula.potential_formula rule and action as CSV; a benign value or apostrophe-escaped formula does not trigger it. Existing input_attachment_csv_mode and output_attachment_csv_mode also control TSV; there is no second tenant policy or added meter. Unsupported or malformed tabular data always fails closed, even under Observe or explicit Off. No macro, binary document or spreadsheet execution is implied.

Try TSV in the dashboard: Connect to an authenticated tenant, open Input data and click Try sample TSV with formula (or select a local CSV/TSV). Set the existing Input CSV formula check to Block if you want the formula held, then click Run input checks. The file picker sends the actual synthetic TSV bytes through the same authenticated API and shows a tsv_structure_recognized_only receipt and the matching formula finding. Use Clear input files to return to text-only checks. After an accepted input, the Output (AI) data step has a separate TSV sample, file picker and Clear control. Neither sample changes a tenant policy or calls an AI model; explicitly saved attachment Off remains not inspected.

The response preserves the normal findings, checker_results, effective_action and evaluation_status and adds an attachments array of safe format/size/hash/reason receipts. Unsupported PDF, Office/ZIP, images, ambiguous encoding, malformed and over-budget files return incomplete/Block without claiming a parser examined them. Do not forward blocked or incomplete attachment contents to an AI model. This feature does not call the model or store a file.

Limitations: Only structurally recognized UTF-8 comma-separated CSV or tab-separated TSV (two or more stable columns and records) and configured existing local formula/security checks are supported; no PDF, DOCX, XLSX or malware scanner is implemented. The existing dashboard has Input and Output file selectors for authenticated tenants: selecting 1–3 real files reads the bytes, encodes them as Base64 and calls the corresponding attachment check endpoint. With no file selected it uses the ordinary text check route. External API clients can submit the same real bytes using attachments_b64; a filename or chat mention alone does not activate attachment inspection. Text-only CSV settings remain backward-compatible when explicitly enabled.
